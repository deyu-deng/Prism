# 调试模式已激活

## 目标

通过系统性的根因分析方法定位和修复缺陷，而非表面修补。

## 调试方法论

### 第一步：重现问题

在动手修复之前，先确保你能稳定复现：

```markdown
## 重现步骤
1. 操作环境: [操作系统/浏览器/Node版本]
2. 前置条件: [需要的数据/配置/状态]
3. 触发操作: [具体操作序列]
4. 期望行为: [应该发生什么]
5. 实际行为: [实际发生了什么]
6. 复现频率: [100% / 偶发 / 特定条件下]
```

### 第二步：收集诊断信息

收集以下信息：

- **错误消息**：完整的堆栈跟踪（非截断版本）
- **日志输出**：相关时间窗口内的日志
- **环境状态**：当时的变量值、请求参数、数据库状态
- **最近变更**：最后一次正常工作后的代码变更

### 第三步：根因分析（5 Whys 方法）

连续问"为什么"直到找到根本原因：

```
现象: 用户登录后看到空白页
  Why 1? → 数据获取 API 返回空数组
  Why 2? → 查询条件缺少 user_id 过滤
  Why 3? → token 解析逻辑在新版本中被改动
  Why 4? → 重构时遗漏了 token payload 结构的变化
根因: token 解析器未适配新的 JWT payload 格式
```

### 第四步：制定修复策略

```markdown
## 修复方案
- **最小修复**: [最快能解决问题的改动]
- **正确修复**: [从根本上解决问题的改动]
- **预防措施**: [防止同类问题再次发生的机制]
```

优先选择正确修复而非最小修复。最小修复仅用于紧急热补丁场景。

### 第五步：编写回归测试

**在修复之前**，先编写一个能复现该 bug 的测试：

```typescript
it('should [正确的预期行为] when [bug触发条件]', () => {
  // Arrange: 构造导致 bug 的输入
  // Act: 执行会触发 bug 的操作
  // Assert: 验证修复后的正确行为
});
```

这个测试在修复前应该**失败**，修复后应该**通过**。

### 第六步：实施修复

- 应用最小必要的代码修改
- 不要借机重构（除非与 bug 直接相关）
- 每次修改后运行完整测试套件

### 第七步：验证修复

- [ ] 回归测试通过
- [ ] 原始复现步骤不再触发问题
- [ ] 无引入新的回归问题
- [ ] 相关集成测试通过

## 调试禁忌（严格禁止）

- 不看堆栈就直接改代码
- 只修症状不找根因（打补丁式修复）
- 借调试之名进行大规模重构
- 删除日志/注释来"清理"而非理解
- 假设"这不可能发生"而不加验证
- 修改代码后不跑测试就提交
- 忽略编译器警告（警告往往是 bug 的线索）

## 常见 Bug 模式参考

### 空值相关
- 未检查 null/undefined 就访问属性
- 可选链遗漏（`obj?.a?.b` vs `obj.a.b`）
- 数组方法返回 undefined（find 返回无匹配）

### 异步相关
- await 遗漏
- Promise 未捕获 rejection
- 竞态条件（并发请求互相干扰）
- 闭包捕获循环变量

### 类型相关
- any 类型的隐式转换
- 类型断言绕过检查（`as any`）
- 泛型约束不足

## Prism 集成

调试流程中：
- 开始时：调用 `prism_update_task` 设置 status=`"debugging"`
- 根因确定后：调用 `prism_write_decision` 记录 RCA（Root Cause Analysis）
- 修复实施前：询问用户确认修复方案
- 修复完成后：调用 `prism_update_task` 设置 status=`"reviewing"`
