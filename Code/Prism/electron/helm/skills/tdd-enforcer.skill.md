# TDD 强制执行模式已激活

## 目标

严格执行测试驱动开发循环：RED → GREEN → REFACTOR。
没有失败的测试，就不写生产代码。

## 循环流程（对每个逻辑单元重复执行）

### RED 阶段：编写失败测试

1. **理解需求** — 代码应该做什么？
2. **先写测试** — 描述期望的行为
3. **运行测试** — 确认它**失败**（如果通过了，为什么？）
4. **如果测试意外通过**：
   - 要么需求已经满足（跳到下一个单元）
   - 要么测试本身有问题（修复测试）

测试命名规范：
```
describe('[功能模块]', () => {
  it('should [期望行为] when [条件]', () => {
    // Arrange — 准备测试数据和依赖
    // Act     — 执行被测行为
    // Assert  — 验证结果符合预期
  });
});
```

断言指导：
- 优先使用精确匹配（`toBe`, `toEqual`）而非真值检查
- 一个测试只验证一个行为点
- 测试即文档：测试名称应该能告诉读者系统做了什么

### GREEN 阶段：最小实现

1. **写刚好足够的代码**让测试通过
2. **暂不重构** — 即使代码丑陋也没关系
3. **运行全部测试** — 确保无回归
4. **如果其他测试失败**：
   - 修复它们（它们暴露了真实问题）
   - 或者判断它们是否为误报

GREEN 阶段规则：
- ✅ DRY 原则可以在此应用（测试内部不要重复自己）
- ❌ 禁止过早优化
- ❌ 禁止超出测试需求的错误处理
- ❌ 禁止顺手添加额外功能（"既然我在这里..."）

### REFACTOR 阶段：提升质量

1. **以绿色测试为安全网**，改进代码：
   - 提取方法增强清晰度
   - 重命名变量提升可读性
   - 减少重复代码
   - 改进错误消息
2. **每步重构后立即运行测试**
3. **如果测试失败**：撤销，换一种方式

重构检查清单：
- [ ] 方法长度 < 20 行
- [ ] 嵌套深度 < 4 层
- [ ] 无魔法数字/字符串
- [ ] 变量命名清晰表达意图
- [ ] 单一职责原则（每个函数只做一件事）

## 反模式（严格禁止）

- 在测试之前编写实现代码
- 以"显而易见"为由跳过测试
- 一次性编写多个失败测试
- 在 GREEN 阶段进行重构
- 提交未测试的代码
- 测试依赖实现细节而非行为
- Mock 所有东西（尽可能测试真实行为）
- 测试只使用 `.toBeTruthy()` / `.toBeFalsy()` 无意义断言

## 测试覆盖范围

### 正常路径
- 正常输入对应正常输出
- 典型用户工作流

### 异常路径
- 无效输入
- 缺失/可选参数
- 空值、null、undefined
- 空数组、空字符串

### 边界情况
- 边界条件（空数组、单元素、最大元素数）
- 并发访问（如果适用）
- 性能极限（大输入量）

## Prism 集成

TDD 循环期间：
- RED 后：调用 `prism_update_task` 设置 status=`"testing"`
- GREEN 后：调用设置 status=`"implementing"`
- REFACTOR 后：调用设置 status=`"reviewing"`
- 卡住超过 30 分钟：调用 `prism_ask_user` 寻求帮助
- 每个循环完成后更新进度
