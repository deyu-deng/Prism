# Plobi 项目宪法 (CONSTITUTION.md)

> **最高宣言：人类拥有战略主权，AI 拥有战术执行权。**  
> 本宪法是 Plobi 软件工程的最高法典。项目内的一切开发活动、架构决策及代码提交，必须无条件服从本宪法确立的“绝对不可谈判的非功能性铁律”。
> 任何违背本宪法的代码或设计均视为“违宪”，坚决予以物理拦截与阻断。

---

## 第一章：非功能性绝对铁律 (The Non-Negotiable Ironclad Laws)

### 第一条：强制垂直切片 (Mandatory Vertical Slices)
1. **定义**：任何功能性变更或新特性的开发，必须以“垂直切片”（Vertical Slice）为最小交付单元。每个切片必须是端到端、可独立演示的完整特性，纵向贯穿所有技术层级（数据库 Schema + API 契约 + UI/UX 交互 + 自动化测试）。
2. **禁止水平开发**：严禁进行“先建数据库表”、“先写纯 API”、“UI 稍后对接”等水平分层式开发。
3. **特例**：仅允许在阶段 0.5 进行极少数纯基础设施搭建（如“配置 Tailwind CSS”、“配置 Tauri 框架”），且每个项目的“基础设施切片”严禁超过 3 个。

### 第二条：强制测试驱动开发与特征测试 (Mandatory TDD & Characterization Tests)
1. **新代码 TDD 铁律**：所有新代码的编写必须遵循严格的测试驱动开发（TDD）循环：
   - **RED（红）**：先编写且只编写一个失败的自动化测试，证明该功能尚未实现。
   - **GREEN（绿）**：编写最小化、最简单的实现代码，让测试变绿。
   - **REFACTOR（重构）**：在测试全绿的安全状态下，进行代码重构，重构期间严禁增加新行为。
2. **遗留代码 Thaw 铁律**：修改任何现有的、缺乏测试的代码（Legacy Code）之前，必须先进行“Thaw（解冻）”：
   - 必须首先编写“特征化测试”（Characterization Tests）以锁定当前的实际行为（即便该行为存在 Bug），建立安全网。
   - 严禁在没有特征化测试保护的情况下，直接修改遗留代码。
   - 经 `fuse` 扫描评级为不可测试的深度技术债模块，必须在 `DEBT.md` 中打上 `LEGACY` 标签并予以物理隔离，新切片严禁依赖这些 Legacy 模块。

### 第三条：绝对禁止硬编码与纯净配置 (Zero-Tolerance for Hardcoding)
1. **零硬编码**：严禁在代码中直接写入任何敏感信息（如 API 密钥、数据库密码、Token 等）、环境特定的配置、幻数（Magic Numbers）或魔法字符串。
2. **配置分离**：所有系统配置、第三方服务端点、特征标志（Feature Flags）必须抽取至显式的环境配置文件（如 `.env`）或中央常量/配置模块中。
3. **自动化审查**：任何包含明文凭证或硬编码环境地址的提交，均在自动代码审查门中直接予以否决。

### 第四条：深度模块设计与零技术债 (Deep Modules & Zero Technical Debt)
1. **深度模块 (Deep Modules)**：倡导“高内聚、低耦合”。模块应当具有极简、干净的外观接口，但隐藏复杂的内部实现细节。严禁编写“浅模块”（Shallow Modules，即接口复杂但内部几乎无隐藏逻辑的透传层）。
2. **禁止上帝函数 (God Functions)**：单函数长度原则上严禁超过 50 行。任何混合了 HTTP 传输、数据库访问、核心业务逻辑与副作用的函数均视为严重架构退化。
3. **技术债容忍度**：未通过自动化测试覆盖的代码绝对禁止进入“冻结区（Freeze）”。任何由 `fuse` 架构扫描发现的严重代码腐烂、不规范依赖，必须立刻写入 `.ai/DEBT.md` 并排入重构队列。

### 第五条：物理文档最高真实性 (Physical Document Sovereignty)
1. **对抗幻觉**：AI 的上下文记忆是短暂且极易退化的。项目的最高真实性仅存在于“物理文档”中，而不是 AI 的对话记忆中。
2. **核心文档库**：
   - 操作者视图（人类可读）：`.docs/PROJECT.md`（愿景与已交付）、`.docs/PROGRESS.md`（当前进度与切片）、`.docs/ARCHITECTURE.md`（模块地图与拓扑）、`.docs/DESIGN.md`（UI/UX 规范）。
   - 执行上下文（AI 可读）：`.ai/CONTEXT.md`（数据契约）、`.ai/DECISIONS/`（决策 ADR）、`.ai/DEBT.md`（技术债）。
3. **冻结线协议**：一旦决策写入 `.ai/CONTEXT.md` 或 `.docs/PROJECT.md`，即进入**冻结状态**。AI 无权单方面修改，只能以追加方式更新。若需修改，必须通过 Mini-Grill 并在 `.ai/DECISIONS/` 中记录正式的 ADR（架构决策记录）。

## 第二章：违宪审查机制 (The Constitutional Review Protocol)

为了确保宪法铁律得到绝对执行，确立以下“违宪审查”前置流程：

> [!IMPORTANT]
> **违宪审查最高指令**：在执行任何实际的编码、重构或配置修改之前，AI 必须首先针对当前任务进行显式的“违宪审查”（Constitutional Review），并向操作者输出审查报告。

### 审查流程规范
1. **触发时机**：每次会话开始、每个垂直切片启动开发前、以及每次进行重大代码修改前。
2. **审查输出格式**：AI 必须在控制台/对话框中首先输出一个独立的 `[CONSTITUTIONAL_REVIEW]` 标记块，并逐项核对以下合规性：
   ```markdown
   ### [CONSTITUTIONAL_REVIEW] 违宪审查报告
   
   - [ ] **铁律一：强制垂直切片** 
     - *核对*：当前任务是否为端到端切片？是否包含 Schema + API + UI + Tests？是否存在水平层割裂？
     - *结论*：[合规 / 违宪并说明]
   
   - [ ] **铁律二：强制 TDD & 特征测试**
     - *核对*：是否已编写失败的自动化测试（RED）？若是修改遗留代码，是否已先编写特征化测试进行 Thaw 隔离？
     - *结论*：[合规 / 违宪并说明]
   
   - [ ] **铁律三：绝对禁止硬编码**
     - *核对*：是否含有任何明文 Key、Magic Strings 或环境配置硬编码？
     - *结论*：[合规 / 违宪并说明]
   
   - [ ] **铁律四：深度模块与零技术债**
     - *核对*：拟改动模块是否保持极简接口？是否存在超过 50 行的上帝函数？是否引入了未隔离的技术债？
     - *结论*：[合规 / 违宪并说明]
     
   - [ ] **铁律五：物理文档冻结线**
     - *核对*：本次修改是否涉及修改已冻结的 `.ai/CONTEXT.md` 或 `.docs/PROJECT.md`？如果是，是否已通过 Mini-Grill 且有对应 ADR？
     - *结论*：[合规 / 违宪并说明]
   
   **【违宪审查结论】**：[ 通过，允许编码 / 拒绝，必须修正设计 ]
   ```
3. **一票否决权**：若上述任何一项核对为“违宪并说明”，编码阶段将**被物理挂起**。AI 必须立刻停止后续的编码动作，向人类操作者报告宪法冲突，并提出合规修正方案。只有在审查结论为“通过”时，方可解锁实际的编码工作。

## 第三章：修正案与否决权 (Amendments and Veto)

1. **宪法修正**：本宪法原则上不可撤销。如因极特殊的技术更迭需要修改宪法条款，必须由人类操作者发起深度 `grill` 会话，达成完全共识后，以“修正案（Amendment）”形式追加写入本文件底部，并在 `.ai/DECISIONS/` 下沉淀对应的最高 ADR。
2. **永久否决权 (Veto)**：凡是被人类操作者以 Veto 机制拒绝的方案，其记录均应永久留存在 `.ai/DECISIONS/VETO-*.md` 中。违宪审查过程中，必须自动比对 Veto 列表，严禁重新讨论或实现已被否决的方案。
